# One-Time-Off read-only source integration

The 5Pay frontend uses its own GAS `bootstrap`, `version`, `content` and `returns` actions and local cache. That endpoint serves a different product and its five-year calculation and strategy rows must not be used for One-Time-Off. No One-Time-Off GAS deployment or endpoint was found or changed.

`server/sheets-readonly.mjs` is a server-side integration component, not a deployed service. It reads A:C of the four financial tabs and A:E of the three official-content tabs in one Google Sheets API `values:batchGet` GET, validates the exact headers, stable IDs, rates, ascending exact years and positive multipliers, then returns the existing v1 envelope. Its SHA-256 revision covers the normalized dataset; `publishedAt` is the time of that source read, not a product publication date. The browser requests an approved same-origin HTTPS endpoint at startup and on reconnect; it validates the envelope, checks cached revision consistency, caches it separately from User data, and falls back to cache or snapshot with a visible status. A read time older than seven days triggers a warning; it is not an official expiry.

## Deployment prerequisites and authorization

1. The Owner must select and authorize an independently operated same-origin HTTPS service and its caller authentication/authorization policy. Mount `officialReadHandler` behind that gateway and supply an `authorize(req)` implementation; the module refuses to construct a handler without one. Its 403 and 503 responses reveal no credentials.
2. Provide a server-only, short-lived Google OAuth access token with `https://www.googleapis.com/auth/spreadsheets.readonly` scope via `getAccessToken()`, for an identity granted viewer access to the specified Sheet. Token acquisition, refresh, secret storage, audience/session authentication, rate limits and infrastructure are responsibilities of that service. Never include a token in frontend code, URLs, logs or browser storage.
3. Set the app's `official-data-endpoint` meta value to the authorized same-origin HTTPS route in the deployment build. Check source authentication, actual permissions, data, CORS/gateway behavior, revision and network/offline behavior end-to-end before describing it as live. Deployment requires separate Owner approval. Do not change the Sheet or existing GAS project.

No credential, service or endpoint has been configured here. Tests use a simulated Sheets API and endpoint; Google access from this environment is denied by network policy. The connected Sheets tool's point-in-time read is not an app runtime credential. Cache integrity depends on the authorized server and browser environment; neither schema checks nor local cache prove provenance.

## Isolated staging procedure (not yet executed)

The production reader and browser intentionally pin the production spreadsheet ID. To prepare a separate staging build without weakening that pin, first create or obtain an isolated Sheet copy containing the same tabs and headers and authorize a **viewer** identity for it. Then run `node tools/create-staging.mjs STAGING_SPREADSHEET_ID`. The command rejects the production ID, creates a new directory under the system temporary directory, replaces the source identity only in that copy, enables `/official` in that copy, and labels its UI STAGING TEST ONLY. Its bundled fallback is merely a copy of the old production snapshot relabelled for the isolated test build; it is not a staging Sheet read or customer data. Never publish or use this build as production.

In a controlled local HTTPS origin, mount the staging copy's `officialReadHandler` behind an explicitly authorized local gateway with a server-side, short-lived viewer token, following the deployment prerequisites above. Bind it to a separate origin and profile so caches cannot mix. With the isolated Sheet's year-20 row at 1.301945, record the returned revision, source-read timestamp and HK$650,972.50 result for HK$500,000. Change only that staging cell to 1.35 using the Sheet owner’s authorized editor; reload or reconnect and record the new source response, changed revision/read time and HK$675,000 result in the actual staging app. In a finally/cleanup step restore the staging cell to 1.301945 and read it back. Verify failures and offline fallback separately, then remove the temporary build and staging copy if appropriate. Never perform this change on the production Sheet.

This procedure needs an isolated Sheet, its editor and reader identities, an approved local or staging HTTPS host and network access to `sheets.googleapis.com`; none were available for this run. Approval for a production endpoint, hosting/authentication policy and deployment remains separate. Empty or missing rows inside an API range fail validation. Without a trusted authoritative year manifest, an omitted otherwise well-formed year cannot be distinguished from a legitimately removed published year; it is not interpolated and its balance remains unavailable.

### Local gateway preparation

`tools/staging-gateway.mjs` exports `startStagingGateway({directory, key, cert, getAccessToken, fetcher})` for a generated temporary staging build. It binds HTTPS to `127.0.0.1` on an ephemeral port, requires the returned random session cookie for every request, rejects the production source ID and unmarked builds, and serves only the app's allowlisted assets and read-only `/official` endpoint. It is a local test harness, not a production authentication system or deployment. A test runner must keep the cookie in its own process and install it in its isolated browser context as Secure, HttpOnly and SameSite=Strict; do not print or transmit it. Close the gateway and remove temporary TLS and app files after testing. `getAccessToken` must supply a short-lived reader token on the server, including refresh/reauthorization as needed; never expose it to the browser. Where the host uses an outbound proxy, provide a proxy-aware `fetcher` that preserves TLS verification. `tests/browser_staging_gateway.cjs` exercises this local gateway and app with **simulated** Sheets responses; it is not real integration evidence.

No copy was created. The Owner must identify and authorize an appropriately protected staging destination (and access for the editor and reader); do not work around the rejection by copying elsewhere without that authorization.

## GAS contract boundary — fixture preparation

No action JSON examples or sanitized GAS responses were supplied in the current task context. `server/gas-contract.mjs` therefore does not pretend to know the external GAS schema. Its `createGasContractReader` requires separately supplied, reviewed parsers for `bootstrap`, `version`, `content`, and `financial` plus a server-owned action transport. The parser boundary returns this **internal model**, not a claimed GAS response format:

- `bootstrap`: `{sourceSpreadsheetId, pageIds}` with the exact Sheet identity and P1–P7 in order.
- `version`: `{revision}` with a safe non-empty revision token.
- `content`: the existing validated `{pages, entries, disclosures}` model (7, 23, 8 with stable IDs).
- `financial`: `{sourceSpreadsheetId, plans}` with the four validated financial tabs and 60 rows.

The reader checks the version before and after the other actions and refuses an inconsistent read, maps only the internal model into the same-origin v1 envelope, and marks `publishedAt` as source-read time. The accompanying test uses deliberately synthetic field names; it is **not** a fixture captured from GAS. Actual examples must be reviewed and mapped with action-specific error handling before enabling this boundary. The current expected 60-row contract fails closed on additions or removals until reviewed; it is not a claim that the Sheet can never change.

For GitHub Pages, a static Pages origin cannot host a server route. A future Owner-approved HTTPS gateway must provide the **same browser origin** for both static app files and `/official` (for example, an authenticated reverse proxy with a custom domain routing static assets to the Pages origin and the official-data route to the gateway). This requires hosting and DNS configuration outside this PR. The gateway must authenticate and authorize callers before any data read; `gasOfficialReadHandler` has no unauthenticated default and offers no arbitrary URL/action proxy. The server-owned GAS transport must pin the supplied endpoint and action allowlist, enforce HTTPS, validate each redirect destination, avoid forwarding credentials across origins, enforce time/size limits, and never return upstream secrets or unvalidated data. Since endpoint access policy and redirect destinations are unverified, no production transport is configured here. An external cross-origin service on a different origin does not satisfy the existing same-origin client, and changing that check or adding a public proxy is not an acceptable substitute. Do not deploy or alter hosting without Owner approval.

### Owner-described GAS action envelopes

The current task specifies these top-level fields: bootstrap `success, service, apiVersion, financial, officialContent, contentRevision`; version `success, service, apiVersion, financialRevision, contentRevision, checkedAt`; content `success, service, apiVersion, revision, readAt, data`; financial `schemaVersion, revision, publishedAt, data`. `server/gas-actions.mjs` implements these envelope checks and compares the financial and content revisions independently before and after the read. It hashes their ordered pair into the existing single envelope revision, without exposing upstream values or credentials. Timestamps are required to be parseable strings for this provisional implementation; the precise deployed representation remains to be confirmed.

The full Code.gs specification and nested payload shapes were not present in the task context. Its pass proves only the documented-field handling and local revision logic, not compatibility with the live deployment.
